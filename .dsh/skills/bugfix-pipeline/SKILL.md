# 审阅门控缺陷修复流水线

## 核心原则

任何 bug 修复都必须走完「问题查找 → 制定计划 → 审阅 → 修复 → 测试 → 收尾 → 汇报」全流程；两道门（审阅、测试）任一不达标即打回重做，不得跳级进入下一阶段。**违反流程的字面规定即违反其精神。**

**先复现，后修复。** 未复现的 bug 不做根因推断，未写回归用例（先红后绿）的修复视为未完成。

## 适用范围与原则

- 本工作流用于 **Mine 工作空间** 的**快速验证**项目（一项目一文件夹）的 **bug 修复**。
- **不回退原则**：修复计划与实现**不得设计「回退/兜底」路径**（依赖失败改用替代库、工具缺失改用预编译产物、无法复现就跳过验证、改用绕过方案掩盖症状）。依赖或工具缺失 → **直接补齐并走主路径**，或如实报告阻塞。审阅据此评估：技术可行性/风险与健壮性维度**不因「未提供回退方案」扣分**。
- **审阅门槛 80 分**（加权总分，满分 100）：≥80 放行，<80 打回。
- **CLI + 离屏渲染硬约束**仍强制（见①问题查找），回归测试必须走无头路径。
- **修复必带回归用例**：凡修复，必配一条先红后绿（TDD）的回归用例，防复发。
- **隔离工作树原则**：每个任务**新开工作树** `.claude/worktrees/<任务名>`（分支 `task/<任务名>`），复现、修复、回归测试全在其中；完成后**合并回 `main` → 主工作区复跑全绿 → 提交 → `git push origin main` → 删除临时工作树**。「合并 + 提交 + 推送」是本流程的强制收尾动作，不是可选步骤；详情见「④ 修复」与「⑥ 收尾」。

## 流程与门控

```
Bug 报告
  │
  ▼
① 问题查找 ──(无头复现 + 根因定位)──▶ 复现报告 + 根因
  │
  ▼
② 制定计划 ──(必须含回归用例设计 + 无头验证)──▶ 计划文档
  │
  ▼
③ 审阅门 ◄──┐   review AGENT 五维加权打分
  │ ≥80 放行 │   <80 → 带反馈打回修订
  ▼          └──(循环直到 ≥80)
④ 修复 ──▶ [开隔离工作树] implement AGENT 先红后绿：回归用例→修复→转绿
  │
  ▼
⑤ 测试门 ◄──┐   [隔离工作树内] test AGENT 全用例跑分
  │ 全绿放行 │   任一失败/跳过 → 修复后重测
  ▼          └──(循环直到 0失败0跳过)
⑥ 收尾 ──▶ finish AGENT:合并回 main → 主工作区复跑绿 → 提交 → push origin main → 删除工作树
  │
  ▼
⑦ 汇报 ──▶ 回主会话输出最终结果
```

## 阶段细则

### ① 问题查找（复现 + 根因）
- 先做**最小无头复现**（CLI 单命令或最小用例），确认 bug 稳定可复现，记录输入/输出对照。
- 再定位**根因**：用 `superpowers:systematic-debugging` 排查，二分/最小化/探针，给出实证（不靠猜测）。
- **硬约束（缺失则整份计划直接打回，不进入审阅打分）**：
  1. **CLI 复现入口**：必须能无头复现 bug（一条 CLI 命令或一个最小测试），可脱离 GUI。
  2. **离屏渲染输出图像**：必须能离屏渲染并落盘一张执行图像（如 PNG），供无头验收与前后对比。
     **离屏渲染 = Vulkan 离屏渲染核心（平台无关一套代码），不依赖窗口/显示服务（Xvfb/X11）**；
     平台差异只允许在软件光栅驱动选型（Linux=lavapipe / Windows=SwiftShader）。
- 产出：`复现命令 + 期望/实际输出 + 根因 + 影响面`（哪些调用方共用出错代码路径）。

### ② 制定计划
- 计划文档落 `docs/superpowers/plans/`（规格/根因说明落 `docs/superpowers/specs/`）。
- 计划必须含：根因、修复方案、**回归用例设计（先红后绿步骤）**、影响面核对、验证方式（无头 CLI + 离屏图像，若涉及渲染）。
- **硬约束**：计划若缺「CLI 复现 + 回归用例」两要素（涉及渲染时再加离屏验证：离屏 = Vulkan 离屏渲染核心，平台无关，不依赖窗口/显示服务，平台差异只在软件光栅驱动选型），直接打回，不进入审阅打分。

### ③ 审阅门（≥80 分放行）
- 派 `review` AGENT，按其输出契约返回五维得分 + 加权总分 + 逐维度扣分原因。
- 总分 ≥80 → 放行进入修复；<80 → 带反馈打回修订计划，重新审阅，循环至达标。

### ④ 修复（TDD 先红后绿，在隔离工作树内）
- **先开工作树**（由主会话执行，只此一次）：
  ```bash
  git -C <Mine 根> worktree add .claude/worktrees/<任务名> -b task/<任务名> main
  ```
  任务名取 `YYYYMMDD-<bug 简述>`（如 `20261105-fix-stale-binary`），与 `docs/superpowers/plans/` 里的计划同名。
- 派 `implement` AGENT，其 prompt **必须写明工作树绝对路径**，并约束：**复现、写用例、改码全部在该工作树内进行，禁止在 `Mine` 主工作区直接改文件**；严格按已通过审阅的计划执行：**先加回归用例并确认红（失败）→ 修复代码 → 确认转绿（通过）**。
- 不得偏离计划中未经审阅的部分；不得为让测试通过而绕过根因。
- 三方库池（`third_party/`、`.user-deps/`）在 `.gitignore` 中，**工作树内不会自带**；需要时在工作树内按 `tools/setup-env.sh` 主路径重新拉取/编译，不回退、不复制主工作区产物。

### ⑤ 测试门（100 分放行，在工作树内跑）
- 派 `test` AGENT，其 prompt 写明同一工作树路径，全用例（含新增回归用例）在该工作树内执行。
- **100 分 = 全用例 0 失败、0 跳过、无回归**，且新增回归用例已确认先红后绿（可查记录）。任一失败/跳过 → 打回修复，重测，循环至全绿。

### ⑥ 收尾（合并 → 复查 → 提交 → 推送 → 拆除工作树）
- 派 `finish` AGENT 按顺序完成，**顺序不可颠倒**：
  1. **合入 main**（工作树内先提交，提交信息 `fix(<模块>): …`）：
     ```bash
     git -C <Mine 根> merge --no-ff task/<任务名> -m "merge: <任务名>"
     ```
     冲突 → 停工如实报告，不得在未验证状态下强推/覆盖。
  2. **主工作区复查**：合并后重新构建 + 重跑测试门，确认 `main` 上全绿（防止「工作树绿、合并后红」）；并核对**用户实际运行的二进制/进程非陈旧**（`pgrep` + 构建时间戳 + debug/release 预设，**用主工作区合并后的新构建核对，不能用工作树里的构建**）。不绿 → 回第 1 步修，**不得推送**。
  3. **提交干净**：在主工作区确认 `git status` 干净；本任务的回归用例/修复/计划文档全部已提交。
  4. **推送到远端**（必做，不是可选）：
     ```bash
     git -C <Mine 根> push origin main
     ```
     推送失败（网络/鉴权/被拒）→ 如实报告阻塞，**不得** `--force` 强推，也不得标记任务完成。
     推送后用 `git -C <Mine 根> status -sb` 确认 `## main...origin/main` **无 ahead**（与远端同步）。
  5. **删除临时工作树**（推送成功后再删）：
     ```bash
     git -C <Mine 根> worktree remove .claude/worktrees/<任务名>
     git -C <Mine 根> branch -d task/<任务名>
     ```
     `worktree list` 必须只剩 `Mine` 主工作区；临时目录残留即收尾未完成。
  6. 清理临时诊断产物/探针、补文档、产出收尾摘要。

### ⑦ 汇报
- 回到主会话，汇总：根因、审阅得分、测试结果（含回归用例先红后绿证据）、变更清单、**合并提交号 + 推送结果 + 工作树已删除证据**、陈旧二进制核对结果、遗留项，作为最终交付说明。

## 审阅五维评分表（bug 修复版）

| 维度 | 权重 | 满分要点 |
|---|---|---|
| 架构合理性 | 25% | 修复点在正确抽象层、模块边界清晰、接口解耦、不破坏既有约定 |
| 问题覆盖性 | 25% | 根因定位准确、修复覆盖全部受影响路径、验收标准可度量可回溯到 bug 报告 |
| 技术可行性 | 20% | 依赖可拉/可编、API 用法正确、版本兼容、无已知 blocker |
| 可测试性 | 15% | 回归用例可独立复现、先红后绿步骤明确、可无头运行 |
| 风险与健壮性 | 15% | 影响面已核对、有错误处理、边界/异常路径已考虑、不引入新回归 |

加权总分 = Σ(维度得分 × 权重)，满分 100，**≥80 通过**，<80 打回。

**评分口径（快速验证项目）**：技术可行性按「主路径能跑通 + 依赖可拉可编」评估；风险与健壮性按「主路径有基本错误处理、阻塞如实报告」评估。**不要求、也不加分于回退/兜底方案设计**。

## AGENT 输出契约

### review AGENT（审阅结果）
```
## 审阅结果
总分：{加权总分}/100 → 通过 / 打回
| 维度 | 权重 | 得分 | 扣分原因 |
| 架构合理性 | 25% | {x} | {原因} |
| 问题覆盖性 | 25% | {x} | {原因} |
| 技术可行性 | 20% | {x} | {原因} |
| 可测试性   | 15% | {x} | {原因} |
| 风险与健壮性 | 15% | {x} | {原因} |
[打回时] 修改建议：{逐条可执行}
```

### test AGENT（测试结果）
```
## 测试结果
用例 {通过}/{总数}，失败 {n}，跳过 {n}
回归用例：{新增用例名} 先红后绿 {已确认/未确认}
结果：100 分（全绿）通过 / 打回
[打回时] 失败用例 + 修复建议
```

## 常见借口（红旗）

| 借口 | 事实 |
|---|---|
| 「bug 明显，不用复现直接改」 | 未复现的修复不作数，①先复现是硬约束 |
| 「改动很小，跳过审阅」 | 审阅门是硬门，跳过即违规 |
| 「测试 90% 通过够用了」 | 测试门只有 100 分，任一失败即打回 |
| 「这 bug 不需要 CLI/离屏验证」 | CLI 复现 + 离屏验证是全局硬约束，无例外 |
| 「先直接修更快」 | 未经审阅的执行作废重来 |
| 「加个绕过/规避处理更稳」 | Mine 是快速验证项目，不做回退/掩盖；缺失即补齐或报阻塞 |
| 「没写回归用例，但手动验过」 | 修复必带先红后绿回归用例，手动验证不算数 |
| 「差 1 分（79）也算过」 | <80 就是打回，无四舍五入 |
| 「这个环境只跑 Linux 就行」 | 渲染核心必须平台无关，双平台同一套测试与 golden；平台差异只在部署/驱动选型 |
| 「bug 就在主工作区顺手改更快」 | 复现/修复/回归必须在 `.claude/worktrees/<任务名>` 内进行，主工作区只接收通过测试门的合并 |
| 「测试绿了，工作树留着下次用」 | 收尾必须合并 + 删除工作树，`worktree list` 只剩主工作区才算完成 |
| 「本地合并完就算交付了，推送以后再说」 | 合并后必须 `git push origin main` 并与远端同步（`status -sb` 无 ahead），推送成功才算完成 |

## 常见错误
- 未复现就猜根因、直接改码 → 修复不可验证，作废重来。
- 描述/计划里省略「CLI 复现 + 回归用例（渲染 bug 再加离屏验证）」硬约束 → 计划直接打回。
- 审阅只给总分不给逐维度扣分 → 无法定位问题，重审。
- 测试只报「通过/失败」不报失败用例与修复建议 → 无法闭环修复。
- 执行阶段擅自扩范围（顺手改无关代码）→ 超出审阅范围的改动视为未审阅。
- 计划里设计回退/兜底路径（替代库、预编译产物、绕过方案）→ 与快速验证原则冲突，修订移除。
- 只验证 release、不核对用户实际跑的二进制/进程（`pgrep` + 构建时间戳）→ 用户仍跑陈旧二进制，视为未交付。工作树内的构建**不能**作为核对对象，必须用合并后主工作区的构建。
- implement/test AGENT 的 prompt 没写明工作树路径，或 AGENT 跑回主工作区改文件 → 视为未隔离，该阶段作废重做。
- 只在工作树里测绿就汇报 → 合并后未在 `main` 复查即视为未交付。
- 合并后没删临时工作树（`.claude/worktrees/<任务名>` 残留）→ 收尾未完成。
- 合并进 `main` 后没有 `git push origin main`（或推送失败却报完成）→ 交付未上远端，视为未交付。
- 推送失败时用 `--force` 强推掩盖问题 → 禁止；如实报告阻塞。
